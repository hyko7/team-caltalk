## 2. 개요와 배경

Team CalTalk은 팀 캘린더와 팀 채팅을 한 화면에 합친 웹 애플리케이션이다.

- 배경: 팀 일정이 개인 캘린더, 메신저, 엑셀에 흩어져 누락·충돌이 생기고(P-01), 일정과 대화가 분리되어 변경 맥락을 추적하기 어렵다(P-02). 팀장이 팀원 일정을 직접 관리하기도 어렵다(P-03).
- 차별점: 일정 변경의 근거가 채팅 이력으로 남는다. 팀원은 본인 관련 일정에 대해 채팅으로 변경을 요청하고(UC-06), 팀장은 그 대화를 보면서 일정을 수정한다(UC-07). 요청 메시지는 일정이 수정되거나 삭제되어도 그대로 남는다(BR-06, BR-15).

## 3. 목표와 성공 지표

### 3.1 비즈니스 목표

- 3,000개 팀(팀당 최대 10명, 약 30,000명)이 동시에 사용할 수 있는 서비스를 제공한다.
- 5일 안에 1인 개발로 MVP(UC-01~12)를 완성한다.

### 3.2 성공 지표 (KPI)

| ID | 지표 | 정의·측정 방법 | 목표 |
|----|------|----------------|------|
| KPI-01 | 일정 누락·충돌 건수 | 파일럿 팀이 주 1회 보고하는 "누락되거나 겹친 일정" 건수. 도입 전 2주 평균(기준선)과 도입 4주 후 2주 평균을 비교한다 | 기준선 대비 50% 이상 감소 |
| KPI-02 | 변경 요청 반영 시간 | 변경 요청 메시지 작성 일시부터 대상 일정의 다음 수정 일시까지 걸린 시간. DB에서 집계한다 | 중앙값 24시간 이내 |
| KPI-03 | 주간 활성 팀 수 (WAT) | 최근 7일 동안 메시지 작성 또는 일정 추가·수정·삭제가 1건 이상 있었던 팀 수. 전체 팀 대비 비율도 함께 본다 | 출시 4주 후 전체 팀의 60% 이상 활성 |

- KPI-02는 Schedule의 수정 일시(도메인 정의서 5장)를 기준으로 집계한다.
- KPI-01은 충돌 자동 감지 기능이 없으므로(범위 밖) 자가 보고로 측정한다.

## 4. 목표 사용자

- 4~10명 규모 팀: IT 개발팀, 스타트업, 소프트웨어 하우스
- 역할은 팀장과 팀원 두 가지다. 권한은 도메인 정의서 3장을 따른다. 페르소나별 상세 시나리오는 작성하지 않는다.

## 5. 범위

### 5.1 포함 (MVP)

- 도메인 정의서 UC-01~UC-12 전체 (UC-12: 이메일+비밀번호 회원가입)
- 반응형 웹 UI (데스크톱, 모바일)

### 5.2 제외

- 알림 (푸시, 이메일 등)
- 반복 일정
- 파일 첨부
- 외부 캘린더·메신저 연동 (Google Calendar, Slack 등, 추후 적용 예정)
- 일정 충돌 자동 감지 (P-01)
- 변경 요청 처리 상태 관리 (BR-06)
- 일정 변경 실시간 푸시 (구성원이 조회할 때 반영)
- 네이티브 모바일 앱
- 접근성 대응

## 6. 기능 요구사항

우선순위: P0 = MVP 필수. MVP 범위가 UC-01~12 전체이므로 모두 P0이다.

| ID | 기능 | 요구사항 | 수용 기준 | 참조 | 우선순위 |
|----|------|----------|-----------|------|:--------:|
| FR-01 | 회원가입 | 이메일, 비밀번호, 이름으로 계정을 만든다 | 이미 가입한 이메일은 거부된다. 비밀번호가 8자 미만이면 거부된다. 가입 후 로그인할 수 있다 | UC-12, BR-01, BR-16 | P0 |
| FR-02 | 로그인 | 이메일과 비밀번호로 인증하고, 소속 팀을 선택해 팀 화면으로 들어간다. 소속 팀이 없으면 팀 생성·초대 코드 입력 화면으로 간다 | 로그인하지 않은 상태의 모든 API·화면 접근은 거부된다. 잘못된 계정 정보는 거부된다 | UC-01, BR-01, BR-10 | P0 |
| FR-03 | 팀 생성 | 팀 이름을 입력해 팀을 만든다. 팀 채팅방이 함께 만들어진다 | 만든 사용자가 팀장이 되고 초대 코드가 생성된다. 팀장은 팀 화면에서 초대 코드를 확인할 수 있다 | UC-09, BR-11, BR-12, BR-17, BR-18 | P0 |
| FR-04 | 초대 코드로 팀 참여 | 초대 코드를 입력해 팀원으로 참여한다 | 유효한 코드면 팀원으로 등록된다. 잘못된 코드는 거부된다. 이미 소속된 팀이면 중복 등록되지 않는다 | UC-10, BR-10, BR-12 | P0 |
| FR-05 | 팀 전환 | 여러 팀에 속한 사용자는 팀 목록에서 팀을 골라 전환한다 | 선택한 팀의 일정과 채팅만 표시된다 | UC-01, BR-09, BR-10, BR-19 | P0 |
| FR-06 | 팀 일정 조회 | 월·주·일 단위를 고르면 해당 기간의 팀 일정을 표시한다 | 선택 기간과 겹치는, 현재 팀의 삭제되지 않은 일정만 표시된다. 다른 팀 일정은 표시되지 않는다. 다른 구성원의 변경은 다시 조회할 때 반영된다 | UC-02, BR-02, BR-09 | P0 |
| FR-07 | 팀 일정 추가 | 팀장이 제목, 시작·종료 일시, 관련 팀원을 입력해 저장한다 | 저장한 일정이 구성원이 조회할 때 보인다. 종료 일시가 시작 일시보다 앞서면 거부된다. 관련 팀원에 팀장이나 다른 팀 사용자를 지정하면 거부된다. 팀원이 시도하면 서버에서 거부된다 | UC-03, BR-03, BR-13, BR-14 | P0 |
| FR-08 | 팀 일정 수정 | 팀장이 채팅을 보면서 기존 일정을 수정한다 | 수정 내용이 구성원이 조회할 때 보인다. 최종 수정자와 수정 일시가 기록된다. FR-07의 검증 규칙이 똑같이 적용된다. 팀원이 시도하면 서버에서 거부된다 | UC-04, BR-03, BR-04, BR-08, BR-13, BR-14 | P0 |
| FR-09 | 팀 일정 삭제 | 팀장이 기존 일정을 삭제한다 (삭제 여부 표시, 논리 삭제) | 삭제된 일정은 캘린더에 보이지 않는다. 그 일정을 참조한 변경 요청 메시지는 남고 대상 일정이 "삭제됨"으로 표시된다. 팀원이 시도하면 서버에서 거부된다 | UC-11, BR-03, BR-15 | P0 |
| FR-10 | 채팅 대화 | 캘린더 옆 채팅방에서 메시지를 주고받는다. 새 메시지는 Long Polling으로 받는다 | 보낸 메시지가 작성자, 작성 일시와 함께 표시된다. 다른 팀 채팅방에는 접근할 수 없다. 새 메시지는 NFR-03 기준 시간 안에 다른 구성원 화면에 나타난다 | UC-05, BR-08, BR-09 | P0 |
| FR-11 | 일정 변경 요청 | 팀원이 본인이 관련 팀원인 일정을 골라 변경 요청 메시지를 보낸다 | 요청 메시지에 대상 일정(제목, 일시)이 함께 표시된다. 관련 팀원이 아닌 일정이나 팀장의 요청은 서버에서 거부된다. 요청에 처리 상태는 없다 | UC-06, BR-05, BR-06 | P0 |
| FR-12 | 변경 요청 반영 | 팀장이 채팅에서 요청을 확인하고 FR-08로 일정을 수정한다 | 수정된 일정이 캘린더에 반영되고, 요청 메시지는 변하지 않고 남는다 | UC-07, BR-06 | P0 |
| FR-13 | 일자별 채팅 이력 조회 | 날짜를 골라 그날의 채팅 이력을 조회한다. 기본값은 오늘(한국 표준시)이다 | 선택한 날짜(한국 표준시 00:00~24:00)에 작성된 메시지만 표시된다 | UC-08, BR-07 | P0 |

### 6.1 데이터 보관 정책

도메인 정의서 BR-20을 따른다.

- 채팅 이력은 무기한 보관한다.
- 사용자가 탈퇴하면 그 사용자가 쓴 메시지는 남기고 작성자 표시만 익명화한다(예: "탈퇴한 사용자"). 탈퇴 기능 자체는 UC-01~12에 없으므로 MVP에서는 정책만 정의하고, 탈퇴 기능을 도입할 때 적용한다.

## 7. 비기능 요구사항

### 7.1 성능·동시성

| ID | 항목 | 기준 |
|----|------|------|
| NFR-01 | 동시 사용 규모 | 3,000팀, 30,000명이 동시에 접속해 Long Polling 연결 30,000개를 유지할 수 있다 |
| NFR-02 | API 응답 시간 | 대기형(Long Polling)이 아닌 API는 목표 부하에서 p95 500ms 이하 |
| NFR-03 | 메시지 전달 지연 | 메시지 전송이 성공한 뒤 같은 팀의 대기 중인 구성원 화면에 표시되기까지 p95 2초 이하 |
| NFR-04 | 처리량 | 약 1,500 req/s (Long Polling 재요청 약 1,000 req/s + 메시지 전송·수신·일정 API) 에서 오류율 1% 미만 |
| NFR-05 | 부하 검증 | D5에 부하 테스트로 NFR-01~04를 확인한다. 미달 시 11장 R-01 대응을 따른다 |

### 7.2 Long Polling 기준

| 항목 | 기준 |
|------|------|
| 요청 방식 | 클라이언트는 마지막으로 받은 메시지 ID를 커서로 보내고, 서버는 그보다 뒤의 메시지를 반환한다 (누락·중복 방지) |
| 대기 타임아웃 | 서버는 새 메시지가 없으면 최대 30초 대기 후 빈 응답을 보낸다 (일반 프록시 기본 타임아웃 60초보다 짧게) |
| 재요청 | 응답을 받으면 즉시 다시 요청한다. 오류가 나면 1초부터 2배씩 늘려 최대 30초 간격으로 재시도한다 |
| 응답 크기 | 한 응답에 최대 100건. 남은 메시지는 즉시 이어서 요청해 받는다 |
| 서버 자원 | 대기 중인 요청은 DB 연결을 점유하지 않는다. 대기는 서버 메모리에서 팀 단위로 관리하고, 새 메시지가 저장되면 해당 팀의 대기 요청만 깨운다 |
| 대상 | 채팅 메시지만 Long Polling으로 받는다. 일정은 조회 시점에 반영한다 |

### 7.3 보안

- 모든 API는 인증을 요구한다(회원가입·로그인 제외). BR-01
- 권한(팀장 전용 기능, 소속 팀 접근, 관련 팀원 여부)은 서버에서 검사한다. 화면에서 버튼을 숨기는 것만으로 처리하지 않는다. BR-03, BR-05, BR-09
- 비밀번호는 bcrypt로 해시해 저장한다.
- 인증 토큰은 HttpOnly, Secure, SameSite=Lax 쿠키로 전달하고 만료는 7일로 한다.
- 로그인 시도는 IP당 분당 10회로 제한한다.
- 초대 코드는 암호학적 난수로 만든 8자리 영숫자이며 팀마다 유일하다.
- 모든 SQL은 파라미터 바인딩을 쓴다. 메시지는 텍스트로만 렌더링한다(HTML 해석 안 함).
- 운영 환경은 HTTPS만 허용한다.

### 7.4 반응형

- 1024px 이상: 캘린더와 채팅을 좌우로 동시에 표시한다 (BR-08).
- 1024px 미만: 캘린더/채팅 탭 전환으로 표시한다. 작은 화면에서 탭 전환으로 대신하는 것은 BR-08에 정의된 예외다.

### 7.5 입력값 제한 (가정)

- 일정 제목 1~100자, 메시지 1~1,000자, 팀 이름 1~50자.

## 8. 기술 제약

| 항목 | 내용 |
|------|------|
| 플랫폼 | 웹 우선. 모바일은 반응형 UI로만 대응 |
| 프론트엔드 | React |
| 백엔드 | Node.js + Express |
| DB | PostgreSQL |
| 실시간 채팅 | Long Polling (WebSocket 사용 안 함) |
| 외부 연동 | 없음 (추후 적용 예정) |
| 일정 반영 | 구성원이 조회할 때 반영 (실시간 푸시 아님) |
| 시간 기준 | 일시는 UTC(timestamptz)로 저장하고, 날짜 경계와 화면 표시는 한국 표준시(Asia/Seoul) 기준 |
| 개발 여건 | 1인 개발, 5일, 1인 개발 수준 예산. 새 인프라 구성요소(메시지 브로커, 캐시 서버 등)는 MVP에 추가하지 않는다 |
