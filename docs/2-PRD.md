## 2. 개요

Team CalTalk은 팀 캘린더와 팀 채팅을 한 화면에 합친 웹 애플리케이션이다. 팀 일정을 한곳에 모으고, 일정 변경과 관련 대화를 같은 곳에서 처리한다.

| 문제 ID | 문제 | 제품의 해결 방식 | 관련 FR |
|---------|------|------------------|---------|
| P-01 | 팀 일정이 여러 곳에 흩어져 충돌하거나 빠진다 | 팀 캘린더 하나에 일정을 모아 팀 구성원 모두에게 공유 | FR-07 ~ FR-10 |
| P-02 | 일정과 대화가 따로 있어 변경 맥락을 추적하기 어렵다 | 캘린더와 채팅을 한 화면에 두고, 채팅 이력을 일자별로 조회 | FR-11 ~ FR-14 |
| P-03 | 팀장이 팀원 일정을 직접 관리하기 어렵다 | 일정 추가·수정·삭제 권한을 팀장에게만 부여 | FR-08 ~ FR-10 |

## 6. 기능 요구사항

모든 FR은 MVP 필수다. 권한·팀 소속 검사는 NFR-03을 따른다.

| ID | 기능 | 내용 | 수용 기준 | 관련 UC / BR |
|----|------|------|-----------|--------------|
| FR-01 | 회원가입 | 이메일, 비밀번호, 이름으로 계정을 만든다 | 가입 후 로그인할 수 있다. 이미 가입한 이메일은 거부된다. 비밀번호가 8자 미만이면 거부된다 | UC-12 / BR-16 |
| FR-02 | 로그인 | 이메일과 비밀번호로 인증하고 JWT 토큰을 발급한다. 회원가입·로그인 외 모든 기능은 유효한 토큰이 필요하다 | 토큰 없이 또는 유효하지 않은 토큰으로 기능을 요청하면 거부된다. 잘못된 이메일·비밀번호는 거부된다 | UC-01 / BR-01 |
| FR-03 | 팀 선택·전환 | 로그인 후 소속 팀을 골라 들어가고, 들어간 뒤에도 다른 소속 팀으로 바꿀 수 있다. 소속 팀이 없으면 팀 생성 또는 초대 코드 입력 화면으로 간다 | 전환하면 선택한 팀의 일정과 채팅만 보인다 | UC-01 / BR-10, BR-19 |
| FR-04 | 팀 생성 | 팀 이름을 입력해 팀을 만든다 | 만든 사용자가 팀장이 되고, 팀마다 유일한 초대 코드와 팀 채팅방이 함께 생성된다 | UC-09 / BR-11, BR-12, BR-17 |
| FR-05 | 초대 코드 확인 | 팀장이 자기 팀의 초대 코드를 본다 | 팀장에게만 표시된다. 팀원이 요청하면 거부된다 | UC-09 / BR-18 |
| FR-06 | 초대 코드로 팀 참여 | 초대 코드를 입력해 팀에 참여한다 | 유효한 코드면 팀원으로 등록된다. 잘못된 코드는 거부된다. 이미 소속된 팀이면 중복 등록되지 않는다 | UC-10 / BR-10, BR-12 |
| FR-07 | 팀 일정 조회 | 월·주·일 단위로 현재 팀의 일정을 본다 | 선택한 기간과 겹치는, 현재 팀의 삭제되지 않은 일정만 표시된다. 다른 팀 일정은 표시되지 않는다 | UC-02 / BR-02, BR-09 |
| FR-08 | 팀 일정 추가 | 팀장이 제목, 시작·종료 일시, 관련 팀원을 입력해 저장한다 | 팀 구성원 조회 시 보인다. 종료가 시작보다 앞서면 거부된다. 관련 팀원에 팀장이나 다른 팀 사용자를 지정하면 거부된다. 팀원의 추가 요청은 거부된다 | UC-03 / BR-03, BR-13, BR-14 |
| FR-09 | 팀 일정 수정 | 팀장이 채팅을 보면서 기존 일정을 수정한다. 작성자와 별도로 최종 수정자와 수정 일시를 기록한다 | 수정 내용이 팀 구성원 조회 시 보인다. FR-08의 입력 검사를 똑같이 적용한다. 팀원의 수정 요청은 거부된다 | UC-04, UC-07 / BR-03, BR-04, BR-06, BR-08 |
| FR-10 | 팀 일정 삭제 | 팀장이 일정을 삭제한다. 데이터는 지우지 않고 삭제 여부만 표시한다 | 삭제된 일정은 캘린더에 보이지 않는다. 그 일정을 참조한 변경 요청 메시지는 남고 대상 일정이 "삭제됨"으로 표시된다. 팀원의 삭제 요청은 거부된다 | UC-11 / BR-03, BR-15 |
| FR-11 | 채팅 대화 | 팀 구성원이 캘린더 옆 채팅방에서 메시지를 주고받는다 | 보낸 메시지가 작성자, 작성 일시와 함께 표시된다. 다른 팀 채팅방에는 접근할 수 없다. 새 메시지는 Long Polling으로 받는다(8장) | UC-05 / BR-08, BR-09 |
| FR-12 | 일정 변경 요청 | 팀원이 본인이 관련 팀원인 일정을 골라 채팅으로 변경 요청 메시지를 보낸다 | 대상 일정이 함께 표시된 요청 메시지가 남는다. 관련 팀원이 아닌 일정은 요청이 거부된다. 요청 메시지에 처리 상태는 없고, 일정이 수정돼도 메시지는 바뀌지 않는다 | UC-06, UC-07 / BR-05, BR-06 |
| FR-13 | 일자별 채팅 이력 조회 | 날짜를 골라 그날의 채팅을 본다 | 선택한 날짜(한국 표준시 00:00~24:00)에 작성된 메시지만 표시된다 | UC-08 / BR-07 |
| FR-14 | 캘린더·채팅 한 화면 배치 | 캘린더와 채팅을 한 화면에 함께 보여 준다 | 넓은 화면에서는 동시에 보인다. 작은 화면에서는 탭으로 캘린더와 채팅을 전환한다 | UC-04, UC-05 / BR-08 |
| FR-15 | 채팅 이력 보관 | 메시지를 기한 없이 보관한다 | 오래된 메시지도 FR-13으로 조회된다. 회원 탈퇴 기능은 이번 개발에서 제외하므로(5.2), 탈퇴 시 익명화(BR-20)는 탈퇴 기능을 도입할 때 적용한다 | BR-20 |
| FR-16 | 로그아웃 | 로그인한 사용자가 로그아웃한다 | 로그아웃하면 로그인 화면으로 돌아가고, 다시 로그인하기 전까지 회원가입·로그인 외 기능을 쓸 수 없다 | - (도메인 정의서에 대응 UC 없음) |

## 7. 비기능 요구사항

| ID | 구분 | 요구사항 | 근거 |

| NFR-03 | 보안·권한 | 로그인 여부, 팀 소속, 팀장 여부, 관련 팀원 여부 검사는 서버에서 한다. 화면에서 버튼을 숨기는 것만으로는 처리하지 않는다. 팀장 여부는 팀 소속 정보의 역할로 판단한다 | BR-01, BR-03~05, BR-09, 도메인 정의서 5장 |

| NFR-06 | 데이터 보존 | 일정은 논리 삭제하고, 채팅 메시지는 무기한 보관한다 | BR-15, BR-20 |

## 8. 기술 제약

| 영역 | 기술 |
|------|------|
| 프론트엔드 | React 19, TypeScript, Zustand, TanStack Query |
| 백엔드 | Node.js, JavaScript, Express, pg 라이브러리 (Prisma 사용 금지) |
| 데이터베이스 | PostgreSQL 17 |
| 플랫폼 | 웹 우선, 모바일은 반응형 웹 UI |
| 실시간 채팅 | Long Polling (WebSocket 사용 안 함). 배포 환경에서 WebSocket 지원이 보장되지 않을 수 있어, 일반 HTTP 요청만으로 동작하는 방식을 쓴다 |
| 개발 조건 | 1인 개발, 2일, 1인 개발에 준하는 예산 |

- 배포 환경(Q-07)은 미정이다.

## 9. 화면 구성

| 화면 | 내용 | 관련 FR |

| 일정 입력·수정 (팀장) | 제목, 시작·종료 일시, 관련 팀원 선택, 삭제 | FR-08 ~ FR-10 |
| 채팅 영역 | 메시지 목록(작성자·작성 일시), 입력창, 날짜 선택으로 일자별 이력 조회. 팀원은 본인 관련 일정을 골라 변경 요청 전송. 요청 메시지에 대상 일정(삭제 시 "삭제됨") 표시 | FR-11 ~ FR-13 |
