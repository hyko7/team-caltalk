# Team CalTalk 프로젝트 구조 설계 원칙

버전 0.5 · 최종 수정일 2026-09-30

참조 문서: `docs/1-domain-definition.md` (도메인 정의서 v0.4), `docs/2-PRD.md` (PRD v0.8), `docs/3-user-scenario.md` (사용자 시나리오 v0.2), `docs/4-wireframes.md` (와이어프레임 v0.5)

## 0. 이 문서를 읽는 법

- 코드를 짜기 전에 "어디에 무엇을 둘지"를 정하는 기준이다. 2일, 1인 개발이므로 최소한의 구조만 정한다.
- 원칙마다 짧은 이유를 붙였다. 이유를 댈 수 없는 구조는 만들지 않는다.
- **(제안)** 표시는 기존 문서에 없는 도구·방식을 가장 단순한 기본값으로 제안한 것이다. 확정이 아니며 8장에 모았다.
- 스택은 CLAUDE.md와 PRD 8장을 따른다. 바꾸지 않는다.

| 영역 | 기술 (확정) |
|------|-------------|
| 프론트엔드 | React 19 + TypeScript + Zustand + TanStack Query, 반응형 웹 |
| 백엔드 | Node.js + JavaScript + Express + pg (Prisma 등 ORM 금지, SQL 직접 작성) |
| 데이터베이스 | PostgreSQL 18 |
| 실시간 채팅 | Long Polling (WebSocket 사용 안 함) |
| 인증 | JWT 토큰, 비밀번호 8자 이상, 원문 저장 금지, SQL 파라미터 바인딩 (NFR-04, NFR-08) |

## 1. 최상위 원칙 (프론트엔드·백엔드 공통)

| 번호 | 원칙 | 이유 |
|------|------|------|
| P1-1 | 문서에 없는 기능은 만들지 않는다. 알림, 반복 일정, 파일 첨부, 충돌 감지, 변경 요청 상태 관리, 회원 탈퇴, 외부 연동은 폴더도 코드도 만들지 않는다 | PRD 5.2, CLAUDE.md "단순함 우선" |
| P1-2 | 미래를 위한 구조를 만들지 않는다. 구현이 하나뿐인 인터페이스, 한 번만 쓰는 추상화, DI 컨테이너, 리포지토리 계층, 빈 폴더를 두지 않는다 | 2일·1인 개발(G-02, R-01). 코드가 늘면 그때 나눈다 |
| P1-3 | 새 인프라를 추가하지 않는다. 메시지 브로커, 캐시 서버, 별도 실시간 서버가 없다. 웹 서버 1개 + PostgreSQL 1개다 | CLAUDE.md 기술 스택 |
| P1-4 | 요구사항 ID를 코드와 커밋에서 가리킨다. 규칙을 구현한 곳에는 주석으로 ID를 한 줄 적는다 (예: `// BR-13`). 커밋 메시지에도 UC/BR/FR/NFR/SC를 쓴다 | 문서와 코드를 이어 주는 유일한 다리 |
| P1-5 | 판단 기준은 문서다. 도메인 규칙은 도메인 정의서, 기술·성능·일정은 PRD를 따른다. 문서끼리 어긋나면 임의로 고르지 않고 사용자에게 알린다 | CLAUDE.md |
| P1-6 | 권한·소속 검사는 서버에서 한다. 화면에서 버튼을 숨기는 것은 보조 수단이다 | NFR-03, BR-01·03·05·09 |
| P1-7 | 일시는 UTC로 저장하고, 날짜 경계와 화면 표시는 한국 표준시(Asia/Seoul)로 한다 | NFR-05, R-04, CLAUDE.md |
| P1-8 | 일정은 논리 삭제하고, 메시지는 지우지 않는다 | NFR-06, BR-15 |
| P1-9 | 폴더는 기능(인증, 팀, 일정, 채팅) 단위로 나눈다. "기술 종류만" 기준으로 잘게 나누지 않는다 | 기능 하나를 고칠 때 열어 볼 파일을 줄이기 위해 |
| P1-10 | 저장소 최상위는 1.1의 구성을 따른다. 앱 코드는 `frontend/`, `backend/` 두 폴더(개발 단계에서 생성 예정)에 두고, 문서는 `docs/`, 작업 도구 설정은 `CLAUDE.md`, `prompts/`, `.claude/`, `.mcp.json`에 둔다. 두 앱 사이에 공유 패키지를 만들지 않는다. 백엔드가 JavaScript라 타입을 공유할 수 없고, API 타입은 프론트엔드에 직접 적는다 | 공유 패키지·모노레포 도구는 설정 비용이 이득보다 크다 |

## 2. 의존성·레이어 원칙

의존 방향은 항상 한쪽이다. 위 레이어는 아래 레이어를 부르고, 아래는 위를 모른다.

### 2.1 백엔드: 3단 (routes → services → db)

```
HTTP 요청
   |
middleware   토큰 확인, 팀 소속·팀장 확인 (NFR-03)
   |
routes       요청 값 꺼내기, 서비스 호출, 응답 보내기
   |
services     비즈니스 규칙 + SQL (BR-13, BR-14 등)
   |
db           pg 연결 풀, 트랜잭션 도우미
   |
PostgreSQL
```

| 번호 | 원칙 | 이유 |
|------|------|------|
| B2-1 | `routes`는 얇게 쓴다. 요청에서 값을 꺼내 서비스를 부르고 결과를 응답으로 돌려주는 일만 한다. 규칙 판단과 SQL을 넣지 않는다 | HTTP 처리와 규칙을 섞으면 규칙을 찾기 어렵다 |
| B2-2 | `services`가 규칙 검사와 SQL을 함께 맡는다. 별도의 리포지토리(쿼리) 계층은 만들지 않는다 | 서비스마다 쿼리가 몇 개 없다. 계층을 하나 더 두면 파일만 늘어난다(P1-2). 서비스 파일이 커지면 그때 나눈다 |
| B2-3 | `services`는 Express의 `req`, `res`를 모른다. 값을 인자로 받고 값이나 오류를 돌려준다 | 규칙을 HTTP 없이 테스트하기 위해 |
| B2-4 | 서비스끼리 서로 호출하지 않는다. 다른 기능의 데이터가 필요하면 SQL로 직접 조회한다 | 서비스 사이의 순환 의존을 막는다 |
| B2-5 | 권한·소속 검사는 `middleware` 한곳에서 한다: 로그인(BR-01) → 팀 소속(BR-09) → 팀장(BR-03). 결과의 역할을 `req`에 실어 서비스에 넘긴다. 서비스에서 팀장 여부를 다시 계산하지 않는다 | 검사 누락이 가장 큰 위험이다(R-03). 팀장 여부는 팀 소속 정보의 역할로 판단한다(NFR-03) |
| B2-6 | 규칙 중 데이터 자체에 걸 수 있는 것은 DB 제약으로도 건다: 이메일 유일(BR-16), 초대 코드 유일(BR-12), 종료 ≥ 시작(BR-14), (사용자, 팀) 중복 소속 금지(UC-10), 변경 요청이면 대상 일정 필수 | 서버 코드에 실수가 있어도 잘못된 데이터가 저장되지 않는다 |
| B2-7 | 관련 팀원 규칙(BR-13)과 변경 요청 대상 규칙(BR-05)은 서비스에서 검사한다. 팀장·다른 팀 사용자 지정은 거부한다 | 여러 테이블에 걸친 규칙이라 DB 제약만으로는 부족하다 |
| B2-8 | 여러 테이블을 함께 바꾸는 작업은 트랜잭션으로 묶는다. 팀 생성(팀 + 팀장 소속 + 채팅방, BR-17)과 일정 저장(일정 + 관련 팀원)이 해당한다 | 반쯤 저장된 데이터를 막기 위해 |
| B2-9 | SQL은 항상 `$1, $2` 파라미터 바인딩으로 실행한다. 문자열 이어 붙이기로 값을 넣지 않는다 | NFR-04, R-05 |
| B2-10 | **Long Polling 대기 중에는 DB 연결을 잡지 않는다.** 새 메시지를 조회한 뒤 바로 연결을 돌려주고, 새 메시지가 없으면 서버 메모리에서 기다렸다가 메시지가 저장되면 깨워 다시 조회한다. 대기 시간에는 상한을 둔다 | 1,000명이 대기해도 연결 풀이 바닥나지 않게 한다(NFR-01, R-02) |

### 2.2 프론트엔드: 4단 (pages → features → stores·lib)

```
pages       화면 한 장. 여러 feature를 조립한다 (WF-01 ~ WF-04/05/06)
   |
features    기능 단위 묶음: 컴포넌트, 서버 통신 훅, 타입
   |
stores      Zustand: 로그인 정보, 현재 팀
lib         fetch 래퍼, 시간 변환, QueryClient
```

| 번호 | 원칙 | 이유 |
|------|------|------|
| F2-1 | `pages`는 `features`를 조립만 한다. 서버 통신과 규칙을 넣지 않는다 | 화면 배치(와이어프레임)와 기능 로직을 분리 |
| F2-2 | `features`끼리 서로 import하지 않는다. 기능 사이에 데이터가 필요하면 `pages`가 props로 넘긴다. 예: 변경 요청 폼의 "내가 관련 팀원인 일정" 목록은 `TeamMainPage`가 일정 훅에서 받아 채팅 쪽에 넘긴다(WF-10) | 기능 간 얽힘 방지 |
| F2-3 | 서버에서 온 데이터는 TanStack Query가 맡고, Zustand는 브라우저 쪽 상태만 맡는다. 서버 데이터를 Zustand에 복사하지 않는다 | 같은 데이터를 두 곳에서 관리하면 어긋난다 |
| F2-4 | Zustand 저장소는 두 개만 둔다: `authStore`(토큰, 로그인한 사용자), `teamStore`(현재 선택한 팀 ID, BR-19). 화면 안에서만 쓰는 값(채팅 보기·숨기기, 입력 중인 내용)은 `useState`로 둔다 | 전역 상태를 최소로 유지 |
| F2-5 | 서버 요청은 `lib/api.ts`의 fetch 래퍼 한 곳으로만 보낸다. 토큰 첨부와 401 처리(→ 로그인 화면, WF-02)를 여기서 한다 | 인증 처리를 한곳에 모은다 |
| F2-6 | 팀을 바꾸면 모든 서버 데이터 조회 키에 팀 ID가 들어 있으므로 이전 팀 데이터와 섞이지 않는다. Long Polling도 팀이 바뀌면 중단하고 새로 시작한다 | BR-19, SC-14 |
| F2-7 | Long Polling은 `features/chat`의 훅 한 곳에서 관리한다. 채팅을 숨겨도(WF-06) 수신은 멈추지 않는다. 화면을 벗어나거나 팀을 바꾸면 진행 중인 요청을 취소한다 | 와이어프레임 WF-06 |
| F2-8 | 버튼을 숨기는 조건(팀장 여부)은 서버가 알려 준 역할로 판단한다. 화면에서 권한을 계산하지 않는다. 숨겨도 서버가 다시 검사한다 | NFR-03 |
| F2-9 | 반응형은 CSS로 처리한다. 넓은 화면은 캘린더·채팅 동시 표시, 좁은 화면은 채팅 보기·숨기기(WF-05, WF-06)다. 폭 기준값은 구현할 때 정한다 | FR-14, 와이어프레임 A-3 |

## 3. 코드·네이밍 원칙

기존 코드가 없으므로 아래를 처음 기준으로 삼는다. 이후에는 기존 스타일을 따른다.

### 3.1 공통

| 번호 | 원칙 | 이유 |
|------|------|------|
| N3-1 | 식별자(파일, 변수, 함수, 테이블)는 영어로 쓴다. 주석과 화면 문구는 한국어로 쓴다 | 도구·라이브러리와 자연스럽게 섞인다. 사용자 문서는 한국어(CLAUDE.md) |
| N3-2 | 도메인 용어는 도메인 정의서 5장의 엔티티 이름을 그대로 쓴다: user, team, membership, schedule, participant, chat room, message | 문서와 코드의 이름이 다르면 추적이 어렵다 |
| N3-3 | 변경 요청은 별도 개념이 아니라 메시지 유형이다(도메인 정의서 5장). `changeRequest`라는 별도 테이블·폴더를 만들지 않는다 | 도메인 정의서, BR-06 |
| N3-4 | 축약어를 쓰지 않는다. 예외: `id`, `url`, `db`, `env` | 읽기 쉽게 |

### 3.2 프론트엔드

| 대상 | 규칙 | 예 |
|------|------|-----|
| 컴포넌트 파일·이름 | PascalCase, 파일명 = 컴포넌트명 | `ScheduleDialog.tsx`, `MessageList.tsx` |
| 페이지 | `~Page` | `TeamMainPage.tsx` |
| 훅 | `use~` camelCase | `useSchedules.ts`, `useMessagePolling.ts` |
| 일반 파일(함수·API·타입) | camelCase | `api.ts`, `types.ts`, `time.ts` |
| 폴더 | 소문자 camelCase 한 단어 | `features/schedules` |
| 변수·함수 | camelCase, 불리언은 `is~`/`has~`/`can~` | `isLeader`, `canEditSchedule` |
| 타입·인터페이스 | PascalCase, `I` 접두어 없음 | `Schedule`, `Message` |
| 상수 | UPPER_SNAKE_CASE | `POLL_TIMEOUT_MS` |
| Zustand 저장소 | `use~Store` | `useAuthStore` |
| 이벤트 핸들러 | 만드는 쪽 `handle~`, 받는 쪽 `on~` | `handleSubmit`, `onSave` |

### 3.3 백엔드

| 대상 | 규칙 | 예 |
|------|------|-----|
| 파일·폴더 | 소문자 camelCase, 기능 이름으로 짓는다. `routes/`, `services/` 안에서 같은 기능은 같은 파일명을 쓴다 | `routes/schedules.js`, `services/schedules.js` |
| 변수·함수 | camelCase, 서비스 함수는 동사로 시작 | `createSchedule`, `listMessagesByDate` |
| 상수 | UPPER_SNAKE_CASE | `POLL_TIMEOUT_MS` |
| 모듈 방식 | ES 모듈(`import`/`export`)로 통일 (제안) | 프론트엔드와 문법 통일 |
| 오류 | 서비스에서 상태 코드가 담긴 오류를 던지고, 오류 처리 미들웨어 한 곳에서 응답으로 바꾼다 | 400 입력 오류, 401 로그인 필요, 403 권한 없음, 404 없음, 409 중복 |

### 3.4 DB

| 대상 | 규칙 | 예 |
|------|------|-----|
| 테이블 | snake_case, 복수형 | `users`, `teams`, `team_memberships`, `schedules`, `schedule_participants`, `chat_rooms`, `messages` |
| 컬럼 | snake_case | `team_id`, `created_at`, `start_at` |
| 기본 키 | `id` | `schedules.id` |
| 외래 키 | `<대상 단수>_id` | `team_id`, `author_id`, `target_schedule_id` |
| 일시 컬럼 | `~_at`, `timestamptz` 타입(UTC로 저장) | `start_at`, `end_at`, `updated_at` |
| 불리언 | `is_~` | `is_deleted` |
| 역할·유형 값 | 영어 소문자 문자열 + CHECK 제약 | `leader`, `member` / `normal`, `change_request` |
| 제약·인덱스 | `테이블_컬럼_종류` | `users_email_key` |

- 화면에 보여 줄 시각은 API가 UTC(ISO 8601)로 내려주고, 프론트엔드 `lib/time.ts`에서 한국 표준시로 바꿔 표시한다(NFR-05).
- DB 컬럼은 snake_case, API JSON은 camelCase다. 변환은 서비스가 응답을 만들 때 한 번만 한다.

폴더 규칙
- 각 feature의 `api.ts`는 서버 요청 함수, `hooks.ts`는 TanStack Query 훅, `types.ts`는 API 요청·응답 타입이다. 파일이 작으면 합치고, 필요 없는 파일은 만들지 않는다.
- 위 트리는 예상 모양이다. 공통 컴포넌트 폴더(`components/`)는 두 feature 이상에서 같은 컴포넌트를 쓰게 될 때 만든다. 지금은 만들지 않는다.
- 초대 코드 확인, 일정 입력 버튼, 변경 요청 버튼은 서버가 알려준 역할이 팀장일 때만 그리며(F2-8), 서버 검사가 진짜 방어선이다.
- 채팅의 날짜 선택은 브라우저 기본 날짜 입력(`<input type="date">`)을 쓰므로 별도 컴포넌트 파일을 만들지 않는다.
- 알림, 온라인 사용자, 최근 활동, [오늘로 이동] 관련 폴더·파일은 없다(9장 미결-1).
- 테스트 파일은 대상 옆에 `*.test.ts`로 둔다(예: `lib/time.test.ts`).

```
│  │  ├─ teams.js              팀 생성(팀·소속·채팅방), 참여, 초대 코드, 구성원
│  │  ├─ schedules.js          일정 CRUD, 논리 삭제, 입력 검사 (BR-13, BR-14)
│  │  └─ messages.js           메시지·변경 요청 저장, 날짜별 조회, Long Polling 대기·깨우기
│  └─ lib/
│     ├─ httpError.js          상태 코드가 담긴 오류 만들기
│     └─ time.js               한국 표준시 날짜 → UTC 시작·끝 시각 변환 (NFR-05)
└─ test/                       API 호출 테스트 (기능별 파일)
```

| 폴더 | 역할 | 근거 |
|------|------|------|
| `src/middleware/` | 모든 요청에 공통인 검사. 권한 검사의 유일한 위치 | NFR-03, R-03 |
| `src/routes/` | URL과 서비스를 잇는 얇은 계층 | B2-1 |
| `src/services/` | 규칙과 SQL. 기능(인증, 팀, 일정, 채팅) 하나가 파일 하나 | B2-2 |
| `src/lib/` | 두 곳 이상에서 쓰는 작은 도구만 | P1-2 |
| `test/` | 거부 케이스 중심의 API 테스트 | T4-1~4 |

폴더 규칙
- DB 스키마(테이블, CHECK·UNIQUE 제약, 인덱스)는 `backend/`가 아니라 `docs/schema.sql`에 둔다(B2-6, T4-7).
- 변경 요청은 `messages` 기능의 한 유형이므로 별도 파일을 만들지 않는다(N3-3).
- 일자별 채팅 이력은 저장하는 대상이 아니라 조회 방법이다(도메인 정의서 4장). 별도 테이블·서비스를 만들지 않는다.
- 기능이 커질 때 서비스 파일을 나눈다. 처음부터 나누지 않는다.
- 팀 구성원 조회(`members`)는 `teams` 기능에 둔다. 일정 저장 시 관련 팀원 검사(BR-13)는 `schedules` 서비스가 SQL로 직접 확인한다(B2-4).
- 로그아웃은 서버에 경로를 만들지 않는다(미결-3).

## 8. 제안으로 표시한 항목

문서에 정해진 것이 없어 가장 단순한 기본값을 제안했다. 확정하려면 사용자 결정이 필요하다.

| 항목 | 제안 | 대안 |
|------|------|------|
| 프론트엔드 빌드 도구 | Vite | Next.js 등은 서버 기능이 필요 없어 제외 |
| 화면 이동(라우팅) | React Router | 화면이 4장뿐이라 상태값으로 전환 |
| 백엔드 모듈 방식 | ES 모듈 | CommonJS |
| DB 스키마 적용 | `docs/schema.sql`을 직접 실행 (마이그레이션 도구 없음) | 마이그레이션 도구 도입 |
| 비밀번호 해시 | Node.js 내장 `crypto.scrypt` | bcrypt 라이브러리 |
| JWT 라이브러리 | `jsonwebtoken` | 직접 구현은 하지 않는다 |
| 백엔드 테스트 | `node:test` + `fetch` | Jest, Supertest |
| 프론트엔드 테스트 | Vitest (최소) | 없음 |
| 린터·포맷터 | ESLint, Prettier 기본 설정 | |
| DB 연결 풀 크기 | 10 안팎에서 시작 | 부하 확인 후 조정 |
| API 경로와 메서드 | 3.5장의 표 | 구현 중 조정 |
| 토큰 보관 위치 | 브라우저 `localStorage` (구현이 가장 단순) | 쿠키(XSS에는 유리하나 CORS·CSRF 설정이 늘어남) |
| Long Polling 대기 | 서버 메모리 대기 목록 + 메시지 저장 시 깨우기, 대기 상한 약 25초 | DB 주기 조회 |
